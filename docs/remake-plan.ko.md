# aitop 전면 개편 기획안

작성일: 2026-11-08 · 상태: 점검 권고안 전체 승인, 구현 착수

이 문서는 설계와 판단 근거를 보존한다. 실제 구현 범위와 제약은 README.md와 CHANGELOG.md를 기준으로 확인한다. 성능 목표와 실계정 호환성은 측정·인증 결과가 아니다.

승인된 조정: 개인 금액 예산·별도 주간 요약·캐시 효율 분석 제외, 화면 모드와 설정·연결 관리 통합, 예측·실시간 세션·다중 계정 UI·Windows·외부 설정 자동 수정·추가 홍보 자료 보류. 기존 6개 서비스는 검증 대상으로 유지하며 `--interval` 저장 동작도 유지한다.

[기획 점검 보고서](plan-review.ko.md)의 권고안이 승인되어 아래 설계에 반영했다. 원래 비교 화면은 참고 시안이며 별도 제품 모드를 의미하지 않는다.

## 1. 권고안

**브랜드와 Rust·Ratatui를 유지하고, 데이터 모델·수집·저장·이벤트 처리·화면을 순서대로 재작성한다.** 개발 버전은 0.2.0-alpha부터 시작하고 검증을 마친 뒤 0.2.0을 공개한다. 개편이라는 이유로 곧바로 1.0을 붙이지 않는다.

제품의 약속은 다음 세 가지다.

1. 지금 남은 한도와 데이터가 확인된 시각을 빠르게 보여준다.
2. 오늘 어떤 프로젝트와 모델에서 사용량이 발생했는지 설명한다.
3. 설치, 진단, 터미널 연동이 간단하고 실패 원인을 사용자가 이해할 수 있다.

초기 사용자는 Claude Code와 Codex를 함께 쓰는 개인 개발자다. macOS를 우선 검증하고 Linux를 같은 코어로 지원한다. Windows는 경로·자격 증명·프로세스 종료까지 별도 검증한 뒤 정식 지원한다.

로컬 검증 결과:

- `cargo test --offline`: 컴파일 성공, **테스트 0개**. 기능의 정확성을 검증한 결과는 아니다.
- `cargo fmt --all -- --check`: 실패. 기존 소스를 자동 포맷하지 않았다.
- `cargo clippy --offline --all-targets -- -D warnings`: 실패, 17개 lint 진단. 스타일 지적과 읽기 오류 반복 가능성 지적이 섞여 있으며, 모두를 기능 버그로 세지는 않는다.
- 저장소에서 CI·테스트 fixture·배포 워크플로를 확인하지 못했다.
- README의 RAM·CPU·기동 시간은 측정하지 않았다. 실제 API와 각 provider의 현행 호환성도 미검증이다.

## 3. 제품 위치와 기능 선택

[CodexBar](https://github.com/steipete/CodexBar)는 여러 provider의 쿼터를 보여주고 CLI도 제공한다. [ccusage](https://github.com/ccusage/ccusage)는 로컬 사용량의 기간별·세션별 보고서를 제공한다. 따라서 멀티 provider, JSON 출력, 기간별 통계만으로 독자적 차별성을 주장하기 어렵다.

aitop은 **터미널에서 상시 켜두기 좋은 통합 모니터의 완성도**에 집중한다. 경쟁 우위는 검증할 가설이며, 성능·사용성 비교를 하기 전에는 우월하다고 홍보하지 않는다.

| 사용자가 해결하려는 일 | 제품 동작 | 완료 판단 |
|---|---|---|
| 작업 전에 잔여 한도 확인 | 한도·리셋·출처·조회 시각을 한 화면에 표시 | 수치가 없는 상태도 명확히 설명됨 |
| 중간 차단을 미리 인지 | 한도 임계치와 리셋 전 사용 추세 표시 | 오래된 값으로 경고하거나 예측하지 않음 |
| 토큰이 어디서 늘었는지 확인 | 오늘/7일/30일, 프로젝트/모델/세션별 상세 | 같은 기간·범위의 상세 합계와 총합이 일치 |
| tmux에서 계속 확인 | 캐시를 읽는 짧은 상태줄 출력 | 상태줄 호출마다 네트워크·전체 로그 스캔이 발생하지 않음 |
| 조회가 안 될 때 해결 | `doctor`가 설치·호환성·접근·데이터 문제를 구분 | 토큰을 출력하지 않고 구체적인 다음 행동 제시 |

초기 범위에서 클라우드 계정, 팀 통합 청구, 웹 서버, 원격 머신 자동 탐색, 자동 계정 전환, 자동 모델 선택, 작업 실행, 임의 셸 명령 플러그인은 제외한다. 로컬 관측 도구의 범위를 유지한다.

## 4. 반드시 지킬 데이터 규칙

### 한도, 이력, 비용을 각각 정의

- **구독 쿼터**: provider 또는 해당 도구가 보고한 사용률·한도·리셋만 표시한다. 토큰이나 API 단가로 구독 쿼터를 만들어내지 않는다.
- **관측된 사용 이력**: 이 컴퓨터에서 읽을 수 있는 이벤트의 합이다. 계정 전체 사용량으로 표현하지 않는다. 원격 세션과 다른 컴퓨터 사용량이 빠질 수 있다.
- **API 환산 비용**: 확인된 모델과 가격표로 계산한 추정치다. 구독 청구액과 분리한다.
- **보고된 비용**: 출처가 제공한 금액이다. 실제 청구 금액인지 도구의 추정 금액인지 의미를 보존한다. 구분 불가하면 실제 청구액이라 표기하지 않는다.

### 출처와 상태는 별도 축

각 메트릭에 `source`, `observed_at`, `fetched_at`, `availability`, `freshness`, `coverage`를 둔다. 화면에는 필요한 정보만 짧게 표시하고 상세에서 전체를 제공한다.

| 축 | 예시 | 의미 |
|---|---|---|
| 출처 | provider API / CLI / statusline / local log | 어디에서 얻었는가 |
| 가용성 | available / unavailable / unsupported | 값이 존재하며 해석 가능한가 |
| 최신성 | fresh / stale / unknown | 관측 시각과 허용 나이에 비춰 유효한가 |
| 완전성 | complete / partial / unknown | 선택 기간·범위의 집계를 얼마나 확보했는가 |
| 갱신 결과 | success / timeout / auth-required / rate-limited / parse-error | 이번 갱신에서 무슨 일이 있었는가 |

캐시는 원래 출처와 관측 시각을 보존한다. 실패 후 캐시를 다시 읽었다는 이유로 최신 값으로 만들지 않는다. 일부 파일 파싱 실패 시 읽은 데이터는 표시할 수 있지만 합계를 부분 집계로 표시한다.

추가 불변 조건:

1. 알 수 없는 값은 `null`/`—`로 표시한다. 관측된 0과 구분한다.
2. 리셋 시각을 지났다고 잔량을 100%로 바꾸지 않는다. 재확인 대기 상태로 바꾼다.
3. 계정·워크스페이스가 다른 쿼터와 이력을 합치지 않는다. 신원이 없는 로컬 이력은 미확인 범위로 분리한다.
4. 전체 합계에 집계 범위·기간·부분 집계 여부를 함께 표시한다. 일부 provider만 알면 그 부분의 합계라고 밝힌다.
5. 입력에 캐시가 포함되는지 provider/스키마별로 정규화한다. reasoning이 출력의 부분집합이면 다시 더하지 않는다.
6. 누적 스냅샷과 증분 이벤트를 구분한다. 재시작·파일 복사·세션 분기·중복 수집으로 사용량이 증가하지 않게 한다.
7. 날짜 집계는 이벤트 발생 시각과 설정된 시간대를 사용한다. 파일 수정일은 재수집 판단에만 사용한다.
8. 가격을 모르는 모델은 토큰만 제공한다. 현재 가격으로 과거 전체를 재계산할 때는 재평가임을 명시한다.

## 5. provider 도입 전략

지원은 서비스 이름 하나에 체크하지 않고, **쿼터·토큰·비용·프로젝트·OS·데이터 소스·검증 버전별**로 공개한다. 목표 상태는 아래와 같으며 현행 호환성을 보증하지 않는다.

| 대상 | 우선도 | 개편안 | 출시에 필요한 검증 |
|---|---|---|---|
| Claude Code | P0 | 로컬 이력 + 공식 statusline 입력의 쿼터 수집 | 필드 부재, 플랜별 차이, 기존 statusline과 공존, 로그 중복 |
| Codex | P0 | App Server의 읽기 인터페이스 + 로컬 이력 | 설치 버전·인증 방식, 다중 버킷, 캐시 토큰 의미, 자식 프로세스 부하 |
| Antigravity | P1 | 구조화된 CLI 보고서 가능 여부를 먼저 검증 | 명령 지원 버전, 출력 스키마, 제한 시간·취소, 무인 로그인/브라우저 실행 여부 |
| GitHub Copilot | P1 | 확인 가능한 쿼터 소스를 독립 어댑터로 구성 | 플랜·API 응답·월간 리셋·로그 제공 범위 |
| Cursor | P1 | 현재 사용량/결제 모델의 실제 데이터 소스부터 재조사 | 현재 endpoint·인증·단위·요청 수/금액 의미 |
| Grok | P2 | 측정 가능한 실제 메타데이터 소스 확보 후 추가 | 쿼터와 토큰을 얻을 수 없으면 unsupported 처리 |

Claude 공식 문서는 statusline JSON의 `rate_limits`와 리셋 필드를 설명한다. 모든 계정·세션에서 항상 존재하는 필드는 아니므로, **사용자가 연동한 뒤 전달되는 관측값**으로 처리해야 한다. 기존 상태줄을 덮어쓰지 않는 연결 방식과 해제/복구 경로를 설계한다. [Claude statusline 문서](https://code.claude.com/docs/en/statusline)

Codex 공식 App Server 문서는 `account/rateLimits/read`, 갱신 알림, 버킷별 한도 구조를 제공한다. 원시 OAuth 파일을 직접 읽고 비공개 URL을 호출하는 현재 방식보다 먼저 검증할 후보이다. 구형 버전·API 키 인증·신원 확인 실패는 별도로 다룬다. [Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)

Claude의 OpenTelemetry는 추가 수집 경로 후보이나 설정 부담이 있어 초기 필수 조건으로 삼지 않는다. 토큰·비용 이벤트를 제공하는 공식 확장 방식이라는 점을 후속 검토에 반영한다. [Claude 모니터링 문서](https://code.claude.com/docs/en/monitoring-usage)

각 provider는 먼저 짧은 기술 검증을 거친다. 문서 확인 → 설치 버전의 capability 확인 → 비식별 fixture 확보 → 정확성 검증 → 실계정 수동 비교 순서다. 비공개 endpoint만 가능한 경로는 실험 기능으로 표시하고 기본 지원 목록과 구분한다. 초기 공개는 Claude·Codex의 검증된 기능을 중심으로 진행하며, 나머지 대상 때문에 출시를 무기한 미루지 않는다.

## 7. 사용 경험과 명령어

첫 실행 흐름은 `설치 → aitop → 로컬 도구 탐지 → 사용 가능한 데이터 표시`다. 탐지는 백그라운드에서 진행한다. 인증되지 않은 도구는 상태와 해결 경로를 표시한다. 첫 실행에서 로그인 브라우저나 Keychain 권한 창이 연속으로 뜨지 않게 한다.

Claude statusline 연결처럼 외부 도구 설정을 바꿔야 하는 기능은 별도 명령에서 변경 내용을 보여주고 실행한다. 백업·충돌 감지·해제 기능을 제공한다. 기존 CLI 로그인은 해당 도구가 관리하도록 한다.

제안 명령어:

```text
aitop                                  # 기본 TUI, 비TTY에서는 텍스트 요약
aitop --once                           # 기존 옵션 유지
aitop --interval 60                     # 기존과 같이 설정에 저장
aitop status --json                     # 버전이 있는 JSON 출력
aitop status --offline                  # 캐시/로컬 데이터만 사용
aitop history --period 7d --group-by project
aitop history --period today --group-by model
aitop providers                        # 기능·상태·소스·검증 버전
aitop doctor                           # 로컬 진단
aitop doctor --network                  # 네트워크 검사 명시적 실행
aitop config                           # 설정 위치와 유효 설정
aitop config set refresh_interval 60    # 설정 영구 변경
aitop demo                             # 인증 없는 고정 예시 데이터
aitop statusline --cached               # P1: 외부 조회 없이 캐시 요약
aitop ingest claude                     # 수동 연결한 statusline JSON 캡처
```

`--interval`의 영구 저장 동작은 유지한다. 기존 `--once`, `-i`는 유지한다. config.json은 검증 후 schema version을 올리고 atomic write로 전환한다. 손상된 기존 파일을 자동 덮어쓰지 않는다.

JSON은 `schema_version`, `generated_at`, provider별 identity/metrics/errors/coverage를 포함한다. 인증 토큰·이메일·대화·전체 프로젝트 경로는 기본 출력에서 제외한다. 사용량 토큰 수는 포함한다. stdout은 결과, stderr는 진단에 사용한다. 종료 코드는 성공 0, 요청한 수집의 부분/전체 실패 1, 인자·설정 오류 2를 기본안으로 고정하고 문서화한다. 스키마와 종료 코드 변경은 릴리스 변경 사항에 포함한다.

TUI 제안 화면 — 아래 수치는 설명용이다.

```text
aitop  | Overview  History  Providers  | Today · local time

Claude Code    5h  64% remaining   resets in 2h 14m
               Source: statusline · observed 18s ago
Codex          5h  81% remaining   resets in 3h 02m
               Source: app-server · observed 6s ago
Cursor             —             authentication required

Observed today     1.24M tokens   API-equivalent estimate $4.82
Coverage           local history · 2 providers · complete
Top project        aitop         620K tokens

[↑↓] Select  [Enter] Details  [Tab] View  [r] Refresh  [?] Help
```

Overview는 쿼터를 우선 표시하고, History에서 집계 상세를 확인한다. 소스 이름이 낯선 사용자를 위해 짧은 설명을 제공하고, 복잡한 정보는 상세 화면에서 확인하도록 검증한다.

## 8. 기술 구조

초기에는 단일 Rust 패키지 안에 라이브러리 코어와 얇은 실행 파일을 둔다. 여러 crate로 미리 쪼개지 않는다. provider 간 독립성은 모듈과 인터페이스로 확보한다.

```text
src/
  lib.rs                # TUI·CLI가 공유하는 코어
  main.rs               # 인자 파싱과 실행 진입
  domain/               # 계정, 메트릭, 쿼터 윈도우, 관측 범위
  providers/            # provider별 탐지·인증 접근·수집·정규화
  ingest/               # 파일 탐색, 스트리밍 파서, 중복 제거, 증분 처리
  storage/              # SQLite, schema migration, 로컬 이력·커서
  runtime/              # 스케줄러, 시간 제한, 취소, 이벤트, source 우선순위
  pricing/              # 모델별 가격·출처·적용일·사용자 override
  config/               # 설정 검증, 이전 버전 변환, atomic write
  cli/                  # status, history, doctor, integrations, JSON
  tui/                  # 상태, 입력 처리, 목록·상세·설정 화면
tests/
  fixtures/             # 비식별 벤더 버전별 로그·응답
  accounting/           # 기간, 누적/증분, 중복, 캐시 토큰
  integration/          # CLI, 프로세스 취소, 파일 회전, 캐시 재시작
```

- **Rust·Ratatui 유지**: 기존 자산과 단일 바이너리 배포 목표에 적합하다. UI를 위해 언어를 바꿀 이유는 아직 없다.
- **Tokio 도입안**: 입력 이벤트·채널·타이머·HTTP·자식 프로세스의 완료를 하나의 취소 가능한 실행 구조로 조율한다. 파일 파싱과 SQLite는 제한된 blocking 작업/저장 워커로 분리한다.
- **reqwest 도입안**: curl 명령 인자로 토큰을 전달하지 않고, HTTP 상태·응답 크기·타임아웃·리다이렉트를 제어한다. 소스가 CLI라면 해당 CLI가 인증을 담당하도록 우선 설계한다.
- **rusqlite 도입안**: 시스템 sqlite3 실행 의존성을 줄이고, 이력과 파일 오프셋을 트랜잭션으로 함께 저장한다. vendor DB 접근은 읽기 전용으로 분리한다.
- **thiserror·tracing 도입안**: 구조화된 실패와 비밀값을 제거한 진단을 구현한다. 원본 응답 전체나 Authorization header를 기록하지 않는다.

도입 버전·최소 Rust 버전은 실제 의존성 해석과 CI에서 결정한다. 현재 README의 Rust 1.75+는 이번 조사로 보증하지 않는다.

### 수집 실행 규칙

1. 캐시를 먼저 렌더링한 뒤 로컬 이력과 쿼터를 독립적으로 갱신한다. 쿼터 조회가 전체 로그 스캔을 기다리지 않게 한다.
2. provider/account/source 단위로 작업을 식별하고 중복 실행을 막는다. 동시 실행 수와 대기열에 상한을 둔다.
3. HTTP·RPC·외부 프로세스에 전체 deadline·응답 크기 상한·취소를 적용한다. 종료 시 aitop이 생성한 자식만 정리하고 회수한다.
4. `429`는 Retry-After를 존중하고, 네트워크 실패에는 지수 backoff와 jitter를 적용한다. 수동 갱신도 강제 제한을 우회하지 않는다.
5. `401/403`, 스키마 불일치, 파일 읽기 오류를 구분한다. 오류 하나가 다른 provider의 최신 결과를 지우지 않게 한다.
6. CLI 인증 파일을 aitop이 임의 갱신하거나 계정을 전환하지 않는다. 재로그인 필요 상태와 해당 도구의 복구 경로를 안내한다.
7. 입력 이벤트, 수집 완료, 상태 메시지 만료, 카운트다운 표시 변경이 화면 갱신을 깨운다. 매 프레임 전체 렌더링하지 않는다.
8. 계정 변경·파일 회전 후 늦게 도착한 결과는 작업 세대와 identity를 확인해 폐기한다.

### 증분 수집과 저장

- 파일 identity·크기·수정 시각·읽은 바이트 위치를 관리한다. 잘린 파일, 교체된 파일, 마지막 미완성 JSONL 줄을 구분한다.
- 완성된 이벤트까지만 커밋하고, 파생 집계와 읽기 위치를 같은 트랜잭션으로 저장한다. 크래시 후 재수집해도 중복되지 않게 한다.
- 공급자 ID가 있는 이벤트는 provider/account/session/event ID로 중복 제거한다. ID가 없는 누적 스냅샷은 세션별 상태와 차분을 보존한다. 해시만으로 모든 중복 문제를 해결했다고 가정하지 않는다.
- 캐시와 stats-cache가 같은 원본에서 파생되었으면 함께 더하지 않는다. 원시 이벤트와 요약 중 우선 소스를 정한다.
- 파일 탐색은 주기적으로 하되 변경 없는 파일의 본문은 다시 읽지 않는다. 파일 감시는 최적화로 추가하고 재탐색으로 누락을 복구한다.
- 기본 저장은 숫자·이벤트 식별자·시간·provider·모델·안전한 프로젝트 식별자다. 대화·코드·자격 증명은 저장하지 않는다. 프로젝트 원본 경로가 필요한 로컬 인덱스는 접근 권한을 제한하고 외부 출력에서 가린다.
- 통계 캐시의 크기/보관 기간을 설정하고, 삭제 시 커서와 집계의 일관성을 유지한다. 설정 초기화, 집계 재구축, 민감정보 없는 진단을 별도 작업으로 제공한다.

설정·캐시 위치는 플랫폼 표준을 따르고 기존 `~/.config/aitop/config.json`을 탐지해 마이그레이션한다. SQLite에는 credentials를 넣지 않는다. 캐시만 읽는 짧은 명령과 수집 프로세스가 함께 실행될 때의 잠금·busy timeout·schema migration을 검증한다.

fixture·fake clock·가짜 HTTP/RPC·테스트용 자식 프로세스로 재현한다. CI에서 실제 사용자 자격 증명과 로그인된 계정을 요구하지 않는다. provider별 실계정 비교는 릴리스 전 별도 수동 검증 항목으로 기록한다.

제안하는 성능 목표는 측정 후 조정한다. 현행 제품의 검증된 성능이나 새 버전의 보장값이 아니다.

- 기준 머신을 고정한 release 빌드에서 첫 TUI 프레임 p95 150ms 이내. 인증·네트워크 완료와 분리 측정.
- 캐시만 읽는 상태줄 출력 p95 100ms 이내.
- CPU는 5분 평균 유휴 1% 미만을 초기 목표로 검증. 카운트다운과 spinner 상태를 분리 측정.
- provider 2개, 초기 인덱싱 종료 상태의 RSS 50MiB 이하를 초기 목표로 검증.
- 합성 로그 1GiB를 스트리밍 처리하고, 변경 없는 재갱신은 로그 본문 재읽기 0바이트. 첫 인덱싱 시간·peak RSS·증분 처리량을 함께 공개.
- 특정 소스가 deadline에 도달해도 키 입력·다른 provider 갱신이 계속 동작해야 한다.

CI는 포맷, Clippy, 테스트, 지원 OS 빌드, 선언된 MSRV 검증을 실행한다. 공급자 버전 fixture와 호환 범위를 릴리스에 기록하고, 실패 시 지원 등급을 내릴 수 있게 한다. 중요 경로의 테스트 통과와 위의 데이터 불변 조건 충족을 출시 문턱으로 삼는다.

## 10. 설치, 발견, README

### 설치와 배포

1. GitHub Releases에 macOS arm64/x86_64와 Linux x86_64 바이너리를 먼저 제공한다. Linux arm64는 검증 runner가 준비되면 추가한다.
2. checksum과 빌드 출처를 제공하고, 패키지 설치 경로에서도 실제 실행을 검사한다.
3. Homebrew tap을 정식 준비해 macOS의 기본 설치 경로로 안내한다. `brew install <실제 tap>/aitop`은 Formula 공개와 설치 검증 후 README에 넣는다.
4. Cargo 패키지는 crates.io 이름·소유권·의존성과 MSRV를 확인한 뒤 게시한다. 사용자는 Rust 없이도 바이너리로 설치할 수 있어야 한다.
5. Windows는 단순 cross compile 성공만으로 지원 배지를 붙이지 않는다. 실제 설치·인증·TTY 복원을 검증한 뒤 배포한다.
6. 자동 업데이트는 초기 범위에서 제외하고 패키지 관리자의 업그레이드 흐름을 따른다.

### README 구성

국제 사용자를 위해 최종적으로 루트 README는 영어, `README.ko.md`는 한국어로 구성하는 안을 권한다. 기존 README.en.md와 한국어 루트 문서의 이동은 실제 개편 릴리스에서 한 번에 수행한다.

첫 화면에서 다음 순서로 답한다.

1. 무엇인가: AI 코딩 도구의 한도와 로컬 사용량을 보여주는 터미널 대시보드.
2. 어떤 모습인가: demo 데이터를 사용해 실제 앱에서 찍은 짧은 영상과 스크린샷.
3. 어떻게 시작하나: 검증된 권장 설치 명령 하나와 `aitop` 실행.
4. 무엇을 지원하나: provider별 쿼터/토큰/비용/OS/필요 설정의 호환표.
5. 수치를 어떻게 읽나: 출처, 조회 시각, 미확인 값, 로컬 이력과 API 환산 비용 설명.
6. 자주 쓰는 명령: TUI, 일회 출력, JSON, history, doctor.
7. 연결이 안 되면: 증상과 doctor 진단에 따른 해결 경로.
8. 더 자세한 내용: provider 문서, 개인정보 처리, 기여 방법, 변경 이력.

소개 문구 초안:

> aitop brings AI coding limits and local usage into your terminal.
> See remaining quotas, reset times, and project-level token usage—with sources and freshness shown alongside the numbers.

실제 측정 전의 0ms/CPU 0%/RAM 8MB, 모든 서비스 zero-config, 모든 값이 실시간이라는 문구를 삭제한다. API 환산 비용을 구독료 절약이나 청구액으로 표현하지 않는다. 계획된 기능은 README 지원 목록에 섞지 않고 roadmap으로 연결한다.

`demo`는 인증 없이 제품을 체험하고, 개인정보 없는 이슈 재현과 문서용 화면 생성을 가능하게 한다. 스크린샷·영상·CLI 예시는 같은 demo fixture에서 생성해 구현과 문서가 어긋나는 것을 줄인다.

### 사람들이 찾아오는 경로

- GitHub 설명에 `AI coding usage`, `quota`, `terminal`, `Claude Code`, `Codex` 등 실제 지원 검색어를 자연스럽게 포함한다.
- 릴리스 페이지에는 설치 파일과 OS/CPU 선택법, 알려진 제한을 먼저 둔다.
- tmux 사용 예시, provider 추가 예제, 빠른 진단 문서를 검색 가능한 별도 문서로 제공한다.
- 템플릿에서 비식별 진단·버전·소스·OS만 요청하고 원본 세션 로그를 통째로 요구하지 않는다.
- 기능 제안과 호환성 문제를 분리한 issue template, CONTRIBUTING, CHANGELOG를 준비한다.
- 핵심 흐름이 검증된 뒤 관련 커뮤니티에 실제 동작 영상과 지원 범위를 공개한다. 별도 랜딩 사이트는 초기 출시의 선행 조건으로 두지 않는다.

성공 지표는 설치 직후 수치를 이해할 수 있는지, 문서만으로 문제를 해결하는지, 업데이트 후 다시 사용하는지로 정한다. 초기에는 수동 사용자 테스트와 공개 이슈로 확인한다. GitHub 다운로드 수는 배포 규모의 참고 지표이며 활성 사용자 수로 간주하지 않는다. 사용 텔레메트리는 기본 도입하지 않는다.

## 11. 실행 순서와 완료 조건

| 순서 | 결과물 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1. 기술 검증 | Claude·Codex 소스별 capability/버전표, 비식별 fixture, 집계 규칙 | 쿼터와 토큰 의미를 실제 데이터와 대조, 불확실한 항목 명시 |
| 2. 정확한 코어 | domain, parser, SQLite 증분 수집, status/history JSON, doctor | 중복·누락·부분 집계·오류 테스트 통과 |
| 3. TUI 개편 | Overview/History/Providers/Settings, 좁은 화면, 키 도움말 | 같은 fixture에서 CLI와 값 일치, 입력·갱신·복원 정상 |
| 4. 공개 베타 | 설치 바이너리, migration, demo, 영·한 README, 호환표 | 깨끗한 macOS/Linux 환경 설치와 사용자 시나리오 검증 |
| 5. 활용 확장 | 알림·상태줄·예측, 우선순위 provider 추가 | stale/중복 알림 방지, 예측 표본 기준, source별 회귀 검증 |

정확한 일정은 1단계에서 정한다. 가장 큰 변수는 provider 소스의 호환성과 로그 스키마다. 일정이 촉박하면 provider 수와 예측 기능을 줄이고, 데이터 의미·오류 처리·설치 검증을 유지한다.

첫 구현 단위는 화면이 아닌 **Claude·Codex의 작은 검증 코어와 `aitop status --json`**으로 권한다. 이 결과가 검증되면 TUI·README·릴리스가 동일한 데이터 계약 위에서 만들어진다.

현재 작업 트리에는 이번 조사 전부터 Cargo.toml·README 등의 변경이 있었다. 해당 변경과 기존 소스는 그대로 보존했다. 이후 구현은 기존 커밋/작업 내용을 확인하고 별도 브랜치에서 진행하는 것을 권한다.

## 12. 그래픽과 화면 개편

추가 요구에 따라 그래픽을 전면 개편 범위에 포함한다. 색상 교체뿐 아니라 정보 배치·밀도·상태 표현·브랜드·README용 시각 자료를 함께 설계한다. 현재 SVG 프리뷰와 TUI는 같은 방향으로 교체하되, 이번 기획에서는 기존 파일을 덮어쓰지 않는다.

### 시각 방향

권장 방향은 **중립적인 터미널 화면에 주요 수치와 경고를 선명하게 드러내는 구성**이다. provider마다 강한 색을 주는 현재 방식은 줄이고, 색을 선택·한도 상태·오류에 일관되게 사용한다.

- 브랜드: 번개 이모지 중심 표기에서 단정한 `aitop` 워드마크와 터미널에서 표현 가능한 작은 막대 모티프로 전환한다. 로고는 SVG로 만들고 ASCII 대체 표기도 제공한다.
- 색상: 터미널 기본 배경을 존중하는 중립 표면, 읽기 쉬운 본문, 절제된 민트 강조를 기본안으로 삼는다. 경고는 황색, 위험은 적색으로 표시하고 상태 문구를 항상 함께 둔다.
- 명암: 작은 회색 글씨에 중요한 수치를 몰아넣지 않는다. provider 이름·잔량·리셋을 우선 읽히게 하고 출처·조회 시각은 보조 계층으로 둔다.
- 타이포그래피: 사용자의 고정폭 글꼴을 사용하고 숫자·단위를 같은 열에 정렬한다. 특수 폰트나 Nerd Font를 필수 조건으로 삼지 않는다.
- 게이지: 긴 블록 게이지와 채움 문자를 줄이고 폭에 맞춰 간결하게 표시한다. 잔량/사용량 기준을 화면에 명시한다. 값이 없으면 게이지를 그리지 않는다.
- 테두리: 전체를 둘러싼 여러 박스보다 구분선·여백·선택 행을 사용한다. 실제 TUI에서 재현할 수 있는 셀 배치를 기준으로 한다.
- 움직임: 최초 수집·수동 갱신 때만 작은 로딩 표시를 쓰고, 의미 없는 점멸·상시 애니메이션은 두지 않는다.

### 통합 화면의 비교 설계 기록

| 구성 | 배치 | 적합한 상황 |
|---|---|---|
| Focus | 쿼터 목록 + 선택한 provider 상세, 좁은 폭에서는 세로 배치 | 기본 화면, 처음 사용하는 사람 |
| Compact | 촘촘한 쿼터 목록 + 아래쪽의 짧은 선택 상세 | tmux 분할·SSH·상시 모니터링 |

두 구성은 비교 설계 기록이며, 실제 제품은 터미널 폭에 따라 배치되는 하나의 화면으로 통합한다. 기획 시안은 `docs/design/aitop-visual-direction.html`에 예시 데이터로 작성했다. 실제 수집·조회 기능이나 완성된 앱 화면을 의미하지 않는다.

Overview는 잔여 한도와 연결 문제, History는 프로젝트/모델별 사용량, Settings는 설정과 연결·호환성을 함께 담당한다. 그래프는 History에 필요한 경우만 사용한다. 좁은 터미널에서는 장식과 보조 열을 줄이고 수치·상태·탐색 수단을 유지한다.

### 테마와 접근성

- 어두운 터미널·밝은 터미널·16색·무색상·ASCII 모드에서 읽을 수 있어야 한다.
- 중요한 상태는 색에만 의존하지 않는다. `Stale`, `Sign-in required`, `Unavailable`처럼 의미를 문자로 표시한다.
- 80×24와 120×30에서 잘림과 스크롤을 검증한다. 더 작은 화면에서는 최소 요약과 상세 진입을 제공한다.
- Unicode 폭, 한글, 긴 모델명·프로젝트명, 글꼴별 기호 차이를 검증한다.
- 그래픽의 새로움보다 같은 수치와 상태가 TUI·일회 출력·문서에서 같은 의미를 가지는 것을 우선한다.

### README와 배포용 그래픽

워드마크, GitHub social preview, 실제 demo 데이터로 생성한 대시보드/설정 화면, 10~20초 사용 영상을 준비한다. README 첫 화면에는 제품이 바로 보이는 장면 하나를 사용하고, 배지·이모지·기능별 장식 이미지는 줄인다. 합성 SVG를 실제 앱 스크린샷으로 소개하지 않는다.

일정에는 데이터 코어 다음의 **시각 설계·TUI 프로토타입 검증**을 별도 작업으로 포함한다. 예시 데이터로 목록·상세·오류·오래된 데이터·빈 상태를 먼저 확인하고, 기능 구현과 문서 촬영으로 이어간다.

## 13. 초기 점검 기록 (아래 후보는 후속 사용자 승인으로 적용)

기존 기능과 신규 제안을 함께 점검한다. 사용자에게 유용한지, 다른 기능과 중복되는지, 유지·검증 비용이 과도한지, 정확한 데이터를 제공할 수 있는지, 핵심 사용 흐름을 복잡하게 만드는지를 기준으로 평가한다. 실제 사용 통계가 없다는 이유만으로 수요가 없다고 단정하지 않는다.

검토 결과는 유지, 개선, 통합 제안, 삭제 제안, 신규 도입 보류로 구분한다. 버그 수정과 기능 제거를 구분해 보고하되, 기존에 제공하던 행동·옵션·provider·출력을 없애는 변경은 삭제 제안에 포함한다. 이름만 바꾸거나 파일을 옮기는 방식으로 삭제 대기 원칙을 우회하지 않는다.

삭제를 제안할 때는 다음 내용을 먼저 보고한다.

1. 대상 기능과 현재 제공하는 가치
2. 불필요하거나 유지하기 어렵다고 판단한 근거와 아직 확인하지 못한 점
3. 영향을 받는 화면·CLI·설정·provider·문서·사용 흐름
4. 삭제, 통합, 기본 숨김, 선택 기능 유지 등 가능한 대안
5. 권고안과 호환성·복구 방안
6. 상태: 사용자 결정 대기

사용자가 승인한 항목과 범위만 제거한다. 답변이 없으면 승인으로 간주하지 않는다. 승인 전에는 해당 기능을 삭제·비활성화하거나 사용자 설정·데이터를 정리하지 않는다. 삭제와 독립적인 조사·설계·검증은 진행할 수 있다.
