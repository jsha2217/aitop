# aitop 개편 기획 점검 결과

점검일: 2026-11-08 · 대상: `remake-plan.ko.md`와 추가한 그래픽 개편안 · 상태: 사용자 전체 권고안 승인, 구현 착수

이번 요청은 작성된 기획을 지금 점검하는 것이다. 앞선 답변의 기존 코드 결함 목록과 향후 점검 절차만으로는 요청을 충족하지 못했다. 이 문서는 승인된 축소안의 근거를 보존한다. 후속 사용자 지시에 따라 기획과 구현에 적용하며 비교 시안은 참고 자료로 남긴다.

## 판단 기준

기획의 중심은 잔여 한도와 리셋을 빠르게 확인하고, 필요한 경우 로컬 사용 이력을 살펴보는 것이다. 이 목적에 직접 기여하는지, 기존 계획과 중복되는지, 데이터로 의미 있는 결과를 낼 수 있는지, 첫 설치를 복잡하게 만드는지로 평가했다.

아래의 삭제 권고는 현재 개편 기획에서 빼자는 제안이다. 모든 사용자에게 영구적으로 가치가 없다는 뜻은 아니다. 특히 구독 중심 사용자와 API 종량제 사용자 중 어느 쪽을 우선할지는 아직 실제 사용자 조사로 확인하지 않았다.

## 1. 기획에서 삭제를 권고하는 기능

| 대상 | 판단 근거 | 제외 시 영향과 남는 대안 | 상태 |
|---|---|---|---|

| 별도 주간 요약 기능 | 이미 최근 7일 History와 프로젝트·모델별 집계가 있다. 별도 요약 기능의 출력·동작·사용 목적이 정의되지 않아 중복 범위가 크다. | 주간 요약 전용 기능은 만들지 않고 7일 History와 JSON을 이용한다. 기간 조회나 주간 데이터 자체를 없애는 것은 아니다. | 삭제 승인됨 |
| 캐시 효율 분석 | 토큰 구성 확인과 별개로 효율을 평가하려면 모델·작업 유형별 기준과 해석이 필요하다. 기본 쿼터 모니터의 목적보다 분석 도구 쪽으로 범위가 넓어진다. | 캐시 효율 점수·분석 화면은 만들지 않는다. 정확한 계산에 필요한 cache read/write 수치와 모델별 집계는 유지한다. | 삭제 승인됨 |

## 2. 중복을 줄이도록 통합을 권고하는 설계

| 대상 | 문제 | 권고안 | 상태 |
|---|---|---|---|
| Focus / Compact를 별도 선택 모드로 구현 | 같은 데이터와 화면을 두 방식으로 각각 관리하면 설정·키 동작·화면 테스트가 늘어난다. 두 이름은 현재 비교 시안으로는 유용하지만 제품 기능 두 개가 될 필요는 없다. | 하나의 화면이 폭에 따라 상세 영역을 옆/아래로 배치한다. 실제 검증에서 필요하면 밀도 설정 하나만 둔다. 두 시안은 설계 참고로 보존한다. | 통합 승인됨 |
| Providers와 Settings를 별도 최상위 화면으로 고정 | 연결 상태 확인, 활성화, 소스 선택, 오류 확인이 서로 다른 화면에 흩어질 수 있다. | 주 탐색은 Overview와 History로 단순화하고, 연결 상태와 설정은 하나의 관리 화면에서 제공한다. CLI의 `providers` 목록과 `doctor` 진단은 목적이 달라 유지한다. | 통합 승인됨 |

## 3. 필요할 수 있지만 출시 약속에서 빼고 보류할 항목

| 대상 | 현재 보류를 권하는 이유 | 다시 도입할 조건 |
|---|---|---|
| 소진 시각 예측 | 한도 스냅샷 수집이 검증되기 전에 예측까지 약속했다. 표본 부족·작업 패턴 변화·리셋으로 예측이 자주 비어 있거나 오해를 줄 수 있다. | 같은 버킷의 충분한 관측 이력과 예측 오차를 실제로 검증했을 때 |
| 활동 중인 세션 실시간 추적 | 지금 필요한 한도·기간별 이력 외에 활동 상태 판정과 별도 갱신 정책이 필요하다. 정적인 세션 상세와 목적이 다르다. | 사용자가 실행 중 세션을 추적해야 하는 구체적인 사용 사례가 확인됐을 때 |
| 다중 계정 UI | 계정별 인증·범위·갱신·선택 상태 관리가 늘어난다. 현재 기록이 여러 계정에 걸쳐 섞이지 않게 하는 기본 정확성은 먼저 필요하다. | 실제 다중 계정 요구와 검증할 계정 환경이 확보됐을 때 |
| Windows 정식 지원 일정 | 파일 경로·인증 저장소·터미널·프로세스 처리를 모두 검증해야 한다. 원안에서도 후속 항목이었으므로 삭제된 기능으로 세지 않는다. | 실제 Windows 검증 환경과 유지 역량이 확보됐을 때 |
| Claude 설정 자동 수정용 integrate 명령군 | 필요한 데이터 경로를 확정하기 전에 preview/apply/remove와 충돌 복구까지 P0로 정했다. 자동 설정 편의가 수집기보다 먼저 커질 수 있다. | 실제 선택한 수집 경로에서 필요성이 입증됐을 때. 초기에는 수동 연결 안내와 진단이 가능한지 비교한다. 사용자 도구 설정을 바꾸는 경우 백업·복구 요건은 줄이지 않는다. |
| 영상·social preview를 모두 출시 필수 산출물로 취급 | 그래픽 개선 자체는 중요하지만 홍보 자료 여러 종류를 동시에 완성할 필요는 없다. | 먼저 새 TUI·워드마크·실제 demo 스크린샷을 완성하고, 사용 흐름이 안정된 뒤 추가한다. |

기본 임계치·리셋 알림과 tmux 상태줄은 후속 기능으로 유지할 가치가 있다. 다만 원안의 0.3 번호만으로 출시를 보장하지 않고, 핵심 수집과 캐시가 검증된 뒤 작업 순서를 정하는 것이 적절하다. 상주 알림 서비스는 이미 필수 계획이 아니므로 새 삭제 대상으로 올리지 않는다.

## 4. 유지해야 하는 항목

다음은 기능 수를 줄인다는 이유로 덜어내면 안 되는 부분이다.

- 쿼터·리셋·오류·조회 시각 표시와 출처 확인. 핵심 수치와 상태는 기본 화면에서, 세부 진단은 상세에서 제공한다.
- 오늘·7일·30일의 토큰 이력과 프로젝트·모델별 집계. 초기 History는 표와 필터로 시작하고 장식적인 차트는 필수로 두지 않는다.
- API 환산 비용의 의미 구분과 알 수 없는 가격 처리. 비용 표시는 보조 정보로 두고 정확한 가격을 아는 범위만 계산한다.
- 캐시 우선 표시, 증분 수집, 중복 제거, 시간 제한, 실패 격리, 설정 보존, 터미널 복구와 관련 테스트.
- `--once`, JSON, 오프라인 조회, `doctor`, provider 상태 목록. 사용자 지원과 자동화에 직접 기여한다.
- `demo`. 문서 이미지·화면 검증·인증 없는 체험에 같은 예시 데이터를 재사용할 수 있다.
- 그래픽 개편, 읽기 쉬운 정보 계층, 좁은 화면, 무색상/ASCII 대응. 사용자가 명시한 개편 요구이며 장식 기능과 구분한다.
- 바이너리 배포, 검증된 Homebrew 설치, 간결한 영·한 README, 지원 기능표와 문제 해결 안내.
- Remaining/Used 전환, 일시정지와 수동 갱신. 현재 구현된 작고 명확한 조작이며, 불필요하다고 제거할 근거가 부족하다. 잔량 표시를 기본값으로 둘 수 있다.

## 5. 기능 외에 바로잡아야 할 기획상 가정

### 초기 provider 범위를 단정하지 않기

Claude·Codex를 기술 검증의 첫 대상으로 삼는 것은 합리적이나, 실제 사용자 수요를 확인하지 않고 나머지 기존 provider를 없애거나 제품 목표를 두 개로 축소할 근거는 없다. 기존 6개 대상을 검증 목록으로 유지하고 기능별 결과를 보고해 출시 범위를 정해야 한다. 조사 우선순위와 지원 종료를 구분한다.

### 화면 선택과 상태 정보가 너무 많아지지 않기

출처·가용성·최신성·완전성·갱신 결과를 내부에서 구분하는 것은 필요하다. 다섯 종류의 상태를 항상 배지로 나열하면 화면이 다시 복잡해진다. 기본 화면에는 정상/문제 상태와 조회 시각만 필요한 만큼 보여주고, 출처·부분 집계 설명은 상세나 해당 합계 가까이에 배치한다.

### 명령 수와 파일 수를 목표로 삼지 않기

제안된 명령어와 10개 디렉터리는 구현 의무로 확정할 단계가 아니다. 공통 데이터 계약과 provider 경계는 유지하되 작은 모듈로 시작한다. Tokio·HTTP client·SQLite는 필요한 책임에 맞춰 선택하고, 스택 목록을 채우기 위해 도입하지 않는다. 증분 수집의 트랜잭션과 HTTP 오류 처리를 단순화하는 의존성은 가치가 있으므로 무조건 줄이지도 않는다.

### 관련 없는 호환성 변경 피하기

`--interval`을 영구 저장에서 세션 한정으로 바꾸자는 제안은 이번 개편의 핵심 문제를 해결하지 않는다. 기존 동작 유지안을 우선 권고한다. 변경할 실제 필요가 생기면 별도 보고한다.

### 명세의 모호한 표현 수정 필요

- JSON 설명의 “토큰 제외”는 인증 토큰을 뜻해야 한다. 입력·출력 등 사용량 토큰 수는 JSON에 포함되어야 한다.
- statusline에서 받은 쿼터는 입력이 도착한 시점의 관측값이다. 앱을 열기만 하면 항상 새 실시간 값을 얻는다고 약속해서는 안 된다. 수집 경로별 동작과 연결 요구를 검증해야 한다.
- “complete”는 선택한 로컬 소스의 처리 범위가 완전하다는 의미로 한정한다. 다른 기기·삭제된 로그·미지원 기록까지 포함한 계정 전체의 완전성을 뜻하지 않는다.
- 버전 번호·성능 목표·지원 플랫폼은 검증할 대상이다. 기획 단계에서 출시 약속이나 측정 결과로 바꾸지 않는다.

## 6. 승인 후 적용할 축소안

초기 개편의 필수 결과는 다음 네 가지로 정리할 수 있다.

1. **믿을 수 있는 쿼터 화면**: 잔량·리셋·조회 상태, 세부 진단.
2. **작고 유용한 History**: 기간·프로젝트·모델별 토큰과 계산 가능한 비용.
3. **단순한 사용 경험**: 하나의 반응형 TUI, 설정·연결 관리, JSON/일회 출력/진단/demo.
4. **실제로 설치 가능한 배포와 문서**: 바이너리·설치 경로·새 그래픽·지원표·README.

개인 예산·별도 주간 요약·캐시 효율 분석은 기획에서 삭제 권고, 화면 모드와 관리 화면은 통합 권고, 예측·실시간 세션 추적 등은 조건부 보류 권고다. 사용자가 전체 권고안을 승인해 적용한다. 실제 구현 범위는 README.md와 CHANGELOG.md를 기준으로 확인한다.
